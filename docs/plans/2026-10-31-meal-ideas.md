# Meal ideas as first-class entities

Date: 2026-10-31
Status: in progress
Scope: `sloppr/` backend. The Angular client is regenerated by a human after the response
contract changes.

## Goal

Generated meal ideas become persisted, addressable resources so they can be approved or
rejected and later turned into recipes.

## Decisions

1. `POST /api/AiInference/meal-ideas` returns `200` + `MealIdeaDTO[]` instead of `string[]`.
   This is a breaking contract change; `sloppr-web` is regenerated with Orval.
2. Approval uses `PUT /api/MealIdeas/{id}/approval` with
   `{ "isUserApproved": true | false | null }` (`null` clears the vote).
   `PUT /api/MealIdeas/{id}` updates the editable scalars (`Name`, `IsUserApproved`).
3. `MealIdea` keeps `Name` only; no description or rationale column.
4. `MealIdea.Name` and `MealIdeaDTO.Name` are `required`. Rejected ideas stay in `GET`
   with `IsUserApproved = false` so a vote can be undone.
5. No unique index on `MealIdea.Name`; the same idea name may recur across generations.
6. No `POST /api/MealIdeas`; generation is the create path.
7. The migration renames the table `MealIdea` to `MealIdeas` for consistency with the other
   tables.
8. Every generated idea links to all ingredients extracted for that prompt through a true
   many-to-many join table explicitly named `MealIdeaKeyIngredients`
   (`MealIdeaId`, `KeyIngredientId`) via the `MealIdeaKeyIngredient` join entity, not EF's
   implicit `KeyIngredientMealIdea`.

## Current-state notes

- The snapshot already contains a `KeyIngredients.MealIdeaId` shadow FK and
  `FK_KeyIngredients_MealIdea_MealIdeaId`, inferred from `MealIdea.KeyIngredients` as
  one-to-many. The migration must replace this with a join table.
- `MealIdea` is currently reached only through `Recipe.MealIdeaId`; there is no
  `DbSet<MealIdea>`.
- `MealIdeaMapper` exists and is registered in `Program.cs`, but nothing uses it.

## Migration expectation

`dotnet ef migrations add MealIdeas` should produce roughly:

- rename `MealIdea` to `MealIdeas`;
- drop `FK_KeyIngredients_MealIdea_MealIdeaId`, `IX_KeyIngredients_MealIdeaId`, and
  `KeyIngredients.MealIdeaId`;
- create join table `MealIdeaKeyIngredients` (`MealIdeaId`, `KeyIngredientId`, composite
  primary key, indexes, cascade FKs);
- no new columns.

The first generated `MealIdeas` migration (`20261031170632_MealIdeas`) used EF's implicit
join table `KeyIngredientMealIdea` and was never applied. Remove it and regenerate after
the explicit join-table config.

Inspect the generated migration before applying it, because the rename and the join table
land together.

## Verification

```bash
cd sloppr
dotnet build
dotnet ef migrations add MealIdeas
dotnet ef database update
dotnet run --launch-profile https
```

Then, with the API running on `http://localhost:5220`:

```bash
cd sloppr-web
npm run codegen
npm run build
npm test -- --watch=false
```

No test project exists in `sloppr/`.

## Out of scope

- Recipe generation and any `Recipes` endpoints.
- Description/rationale generation for ideas (would change the LLM response shape).
- Auth, pagination, filtering by approval state, and caching.
- Hand-written Angular changes; `sloppr-web/src/app/api/` stays generated.
