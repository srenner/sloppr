# Meal ideas as first-class entities

Date: 2026-10-31
Status: in progress — chunks 1–5 done; resume at chunk 6
Scope: `sloppr/` backend. The Angular client is regenerated by a human after the response
contract changes.

## Goal

Generated meal ideas become persisted, addressable resources so they can be approved or
rejected and later turned into recipes.

## Decisions

1. `POST /api/AiInference/meal-ideas` returns `200` + `MealIdeaDTO[]` instead of `string[]`.
   This is a breaking contract change; `sloppr-web` is regenerated with Orval.
2. Approval uses `PUT /api/MealIdeas/{id}/approval` with
   `{ "isUserApproved": true | false | null }` (`null` clears the vote).
   `PUT /api/MealIdeas/{id}` updates the editable scalars (`Name`, `IsUserApproved`).
3. `MealIdea` keeps `Name` only; no description or rationale column.
4. `MealIdea.Name` and `MealIdeaDTO.Name` are `required`. Rejected ideas stay in `GET`
   with `IsUserApproved = false` so a vote can be undone.
5. No unique index on `MealIdea.Name`; the same idea name may recur across generations.
6. No `POST /api/MealIdeas`; generation is the create path.
7. The table is `MealIdeas` (renamed from `MealIdea`).
8. Every generated idea links to all ingredients extracted for that prompt through a true
   many-to-many join table named `MealIdeaKeyIngredients`
   (`MealIdeaId`, `KeyIngredientId`) via the `MealIdeaKeyIngredient` join entity.

## Chunk 6 implementation notes

Add `UpdateAsync(MealIdea idea)` to `IMealIdeaService` / `MealIdeaService`, matching
`KeyIngredientService`:

```csharp
public async Task<MealIdea> UpdateAsync(MealIdea idea)
{
    _uow.Repository<MealIdea>().Update(idea);
    await _uow.CompleteAsync();
    return idea;
}
```

Add two request DTOs:

```csharp
public class MealIdeaUpdateRequest
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public bool? IsUserApproved { get; set; }
}

public class MealIdeaApprovalRequest
{
    public bool? IsUserApproved { get; set; }
}
```

Controller actions:

- `PUT /api/MealIdeas/{id}` — `400` when `id != request.Id` (existing controller
  pattern); load with **plain `GetByIdAsync`**, `404` if missing; set `Name` and
  `IsUserApproved`; `UpdateAsync`; `204`.
- `PUT /api/MealIdeas/{id}/approval` — load with **plain `GetByIdAsync`**, `404` if
  missing; set `IsUserApproved` (`true`/`false`/`null`); `UpdateAsync`; `204`.
- `DELETE /api/MealIdeas/{id}` — load with **plain `GetByIdAsync`**, `404` if missing; set
  `IsDeleted = true`; `UpdateAsync`; `204`.

Load plain, not `GetByIdWithIngredientsAsync`: `Repository.Update` walks the tracked graph
and would mark included `KeyIngredient` rows as `Modified`.

Recorded defaults (change before starting if not wanted):

- Keep the `Id` field and the `400` mismatch check.
- Do not add whitespace validation; match existing controllers (`required` only).
- Soft delete sets `IsDeleted` only. Deleted ideas therefore stay hidden from both
  `GET /api/MealIdeas` and `GET /api/MealIdeas/inactive` (the latter filters
  `IsActive == false`). Leave that quirk as-is for chunk 6.

Add the three requests to `sloppr.http`.

No migration is needed for chunk 6.

## Endpoints after completion

| Verb | Route | Body | Result |
|---|---|---|---|
| `POST` | `/api/AiInference/meal-ideas` | `{ "prompt": "..." }` | `200` `MealIdeaDTO[]` |
| `GET` | `/api/MealIdeas` | – | `200` `MealIdeaDTO[]` (filtered) |
| `GET` | `/api/MealIdeas/inactive` | – | `200` `MealIdeaDTO[]` (`IgnoreQueryFilters`, then `IsActive == false`) |
| `GET` | `/api/MealIdeas/{id}` | – | `200` / `404` |
| `PUT` | `/api/MealIdeas/{id}` | `{ "id": 0, "name": "...", "isUserApproved": null }` | `204` / `400` / `404` |
| `PUT` | `/api/MealIdeas/{id}/approval` | `{ "isUserApproved": true }` | `204` / `404` |
| `DELETE` | `/api/MealIdeas/{id}` | – | `204` soft delete / `404` |

Routes use `{id}`, matching the existing controllers. The literal `inactive` segment wins
over `{id}` in routing.

## Migration

Applied: `20261031171751_MealIdeas`.

- renames `MealIdea` to `MealIdeas`;
- drops `FK_KeyIngredients_MealIdea_MealIdeaId`, `IX_KeyIngredients_MealIdeaId`, and
  `KeyIngredients.MealIdeaId`;
- creates join table `MealIdeaKeyIngredients` (`MealIdeaId`, `KeyIngredientId`, composite
  primary key, indexes, cascade FKs);
- adds no new columns.

The earlier `20261031170632_MealIdeas` used EF's implicit `KeyIngredientMealIdea` join
table and was replaced before applying.
