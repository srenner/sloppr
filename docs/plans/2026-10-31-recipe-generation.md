# Recipe generation and markdown output

Date: 2026-10-31
Status: ready — implements work items 4–5 of
[`2026-10-31-recipe-templates.md`](2026-10-31-recipe-templates.md)
Scope: `sloppr/` backend. `sloppr-web` is regenerated by a human after the contract
changes.
Branch: `recipe-generation`

## Goal

Turn an approved meal idea into a stored recipe using the current recipe format, and
expose the stored recipe as markdown.

Flow: pick a meal idea → generate → persist → render.

## Decisions

1. `POST /api/AiInference/recipes/{mealIdeaId}` persists the recipe and returns
   `201 RecipeDTO` (`CreatedAtAction` → `GET /api/Recipes/{id}`).
2. Generation reuses `IRecipeService.AddAsync`, so the current format row, the
   `FormatKey`/`FormatVersion` stamp, and `RecipeFormatValidator` stay in one place.
3. Bad AI output (parse, deserialize, or validator failure) returns `502` with the error
   list. Bad manual input on `/api/Recipes` stays `400`.
4. The prompt lives in `appsettings.json`; the format rules are passed to the model as
   context from the current `RecipeFormats` row's `Rules` JSON.
5. The model comes from `ApplicationSetting.RecipeModelId` (column already exists).
6. Markdown is read-only over a stored recipe. One built-in layout, no custom layouts,
   no streaming.
7. Unknown or missing meal idea → `404`.

## Work

### 1. Prompt setting

- `sloppr/Settings/AiSettings.cs`: add `RecipeGenerationPrompt`.
- `sloppr/appsettings.json` (`AI` section): strict-JSON prompt describing the standard v1
  shape (info, ordered ingredients, ordered steps, optional groups) and forbidding prose
  or code fences.
- `sloppr/appsettings.Development.json`: only if it overrides the whole `AI` section.

### 2. Generation DTO and mapper

- Add `sloppr/DTOs/RecipeGenerationResponse.cs` (or a model-shape DTO under `Recipes/`)
  mirroring the editable fields: name, description, serving count, prep/cook minutes,
  difficulty, notes, ingredients, steps.
- Map it to `Recipe` with `MealIdeaId` set. Either extend `RecipeMapper` with a partial
  method or map explicitly in the service; do not hand-edit generated code.

### 3. Chat service

- `sloppr/Services/ChatService.cs`: add
  `Task<Recipe?> GenerateRecipeAsync(MealIdea idea, string formatRules)`.
- Load the model through `_modelService.GetByIdWithProviderAsync(RecipeModelId)`.
- Build the user message from the idea name, the idea's key-ingredient names (loaded with
  `GetByIdWithIngredientsAsync`), and the format rules JSON.
- Request `ChatOptions { ResponseFormat = ChatResponseFormat.Json }`, deserialize, and
  return `null` (or throw a known exception) on parse failure so the controller can map it
  to `502`.

### 4. Endpoint

`sloppr/Controllers/AiInferenceController.cs`:

1. `mealIdeaService.GetByIdWithIngredientsAsync(mealIdeaId)` → `404` if missing.
2. Load the current `RecipeFormats` row (`IsCurrent && Key == RecipeFormat.Key`) → `502`
   if absent.
3. `chatService.GenerateRecipeAsync(...)` → `502` if generation or parsing fails.
4. Set `MealIdeaId`, call `recipeService.AddAsync(recipe)` → `502` with
   `result.Errors` if invalid.
5. Return `201` with `RecipeDTO` via `CreatedAtAction(nameof(RecipesController.GetRecipe))`.

Register nothing new in `Program.cs`; `ChatService` and `IRecipeService` are already
injected services.

### 5. Markdown output

- Add `sloppr/Recipes/RecipeMarkdownRenderer.cs`: `static string Render(Recipe recipe)`.
- Layout: title, description, servings / prep / cook / difficulty line, optional notes,
  `## Ingredients`, `## Steps`.
- Ingredients: one line each, `quantity unit name` with the optional note, prefixed with
  `- `. Steps: numbered from 1.
- Groups: emit a `### <Group>` heading when the group changes; a blank group renders
  under the section heading with no subheading.
- `RecipesController`: `GET /api/Recipes/{id}/markdown` → `404` or
  `Content(markdown, "text/markdown; charset=utf-8")`. Use the loaded recipe; no extra
  query.

### 6. Request file

- Add both routes to `sloppr/sloppr.http` with realistic bodies.

## Contract after this chunk

| Verb | Route | Body | Result |
|---|---|---|---|
| `POST` | `/api/AiInference/recipes/{mealIdeaId}` | – | `201` `RecipeDTO` / `404` / `502` |
| `GET` | `/api/Recipes/{id}/markdown` | – | `200` `text/markdown` / `404` |

## No migration

`ApplicationSetting.RecipeModelId` and the `RecipeFormats` seed already exist. No model
or `ApplicationDbContext` changes are expected. If the generation DTO lives in `DTOs/`,
nothing is persisted differently.

## Human steps

1. `cd sloppr-web && npm run codegen` with the API on `http://localhost:5220`.
2. `npm run build` and `npm test -- --watch=false`.

## Verification

```bash
cd sloppr
dotnet build
dotnet run --launch-profile https
```

Then, with a seeded model and `RecipeModelId` set:

1. `POST /api/AiInference/meal-ideas` to create ideas.
2. `PUT /api/MealIdeas/{id}/approval` if the workflow requires approval.
3. `POST /api/AiInference/recipes/{mealIdeaId}` → `201` with ingredients and steps.
4. `GET /api/Recipes/{id}/markdown` → readable markdown; grouped recipes show group
   headings.
5. Force a bad response (e.g. stop Ollama) → `502`, no recipe row created.

## Out of scope

- Streaming generation, regeneration or overwrite semantics, and draft-only responses.
- Editing the AI response before saving; the client edits through
  `PUT /api/Recipes/{id}`.
- Custom or user-selectable markdown layouts, HTML/PDF export, and images.
- Any `sloppr-web/src/app/api/` edits.
